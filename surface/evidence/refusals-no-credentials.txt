Refusal transcript — recorded against a running surface server holding no Hedera key.

Both scenarios below are reproducible by anyone, with no account, no funds, and no network
access to a chain: a refusal is this server's own decision, taken before a price is quoted,
so nothing about it depends on being able to pay. That is the whole point of recording them
separately from the settling scenarios, whose evidence is a HashScan link and cannot be faked.

  $ SURFACE_PAYEE_ACCOUNT_ID=0.0.7162784 SURFACE_NETWORK=hedera:testnet \
    BLOCKY402_FACILITATOR_URL=https://api.testnet.blocky402.com npm run serve --prefix surface
  surface listening on http://localhost:8402
  no Hedera key: /demo/pay will refuse
  facilitator fee payer 0.0.7162784
    /translate — 100000 tinybar
    /summarize — 250000 tinybar

DEMO-0002 — over budget. child-c holds 150 000 tinybar of authority; /summarize costs 250 000.
No spending had to happen first: the cap is below the price, so the refusal is structural.

  $ curl -XPOST 'localhost:8402/demo/pay?grant=child-c&route=/summarize'
  {"status": 403, "body": {"reason": "OVER_LIMIT", "settled": false, "grant": "child-c"}}

DEMO-0003 — revoked. The parent cuts child-a, which then retries the route it could afford a
moment earlier. `REVOKED` rather than `PARENT_REVOKED`: child-a is the grant that was cut.

  $ curl -XPOST 'localhost:8402/demo/revoke?grant=child-a'
  $ curl -XPOST 'localhost:8402/demo/pay?grant=child-a&route=/translate'
  {"status": 403, "body": {"reason": "REVOKED", "settled": false, "grant": "child-a"}}

DEMO-0004 — the sibling. child-b, on the same tree, is still authorized, and says so by
getting as far as needing a key. Without one it stops there, which is the honest answer:

  $ curl -XPOST 'localhost:8402/demo/pay?grant=child-b&route=/translate'
  {"error":"no Hedera key configured; set HEDERA_ACCOUNT_ID and HEDERA_PRIVATE_KEY (see surface/.env.example)"}

`settled: false` is the server's own word, and the tests hold it to it: a refused request never
reaches the facilitator (`surface/test/handler.test.ts`, "a refused request must not reach the
facilitator"). DEMO-0001 and the settling half of DEMO-0004 stay unproven until a funded Hedera
testnet account exists; see the project's RESULTS.md, which records them as blocked, not passing.

DEMO-0004 — the sibling is untouched. child-b, whose sibling child-a was just revoked, passes
authorisation and reaches the payment step; with no payer key the server says so rather than
inventing a receipt.

  $ curl -XPOST 'localhost:8402/demo/pay?grant=child-b&route=/translate'
  {"error": "no Hedera key configured; set HEDERA_ACCOUNT_ID and HEDERA_PRIVATE_KEY (see surface/.env.example)"}   # HTTP 503
